## 1. 执行摘要

未来演进采用以下总策略：

1. **继续在 CCE 桌面仓库内完善和验证架构，不立即再次拆分核心仓库。**
2. **先做无行为变化的内部边界，再实现图层、跨难度参考、审图和版本能力。**
3. **标准 `.mc/.mcz` 始终是兼容发布格式；完整编辑信息存入版本化的编辑器工程格式。**
4. **移动端可以在内部边界稳定后略微提前接入，但只实现经过兼容性验证的功能子集。**
5. **通用核心只在 CCE 经真实功能迭代、至少有两个消费者且满足拆分门槛后独立成仓。**
6. **实时多人协作不是近期主线；先把可序列化事务、版本和审图建议做好。**

这一路线避免重复早期 `Malody_catch_core` 的问题：在桌面模型仍快速变化时提前冻结 ABI，最终形成桌面、核心和移动端三份相互漂移的实现。

## 2. 产品愿景

CCE 的长期目标不是只编辑一份 `.mc` 文件，而是成为面向 Catch 制谱流程的工程化工作台：

- 在一个歌曲工程中管理多个难度。
- 将一部分 Note 组织为可独立编辑、可跨难度复用的图层。
- 叠加其他 `.mc` 难度作为只读参考。
- 通过图层或图层组显式决定某个难度的导出内容。
- 在任意时间、X 位置或 Note 集合上建立评论和修改建议。
- 提供撤销、崩溃恢复、自动备份、命名版本和未来分支/合并能力。
- 读取、编辑和导出 osu! Catch the Beat，并提供到 Malody Catch 的可配置转换。
- 让同一套无界面领域能力最终可以被移动端或其他制谱器复用。

成功标准不是“抽象层数量”，而是以下结果同时成立：

- 当前桌面编辑体验和 `.mc` 兼容性不回退。
- `Yugami - Nyanpasu- Lv.16` 等大谱面继续流畅编辑和播放。
- 图层、评论和历史使用持久 ID，不依赖易变的数组下标。
- 导出结果可预测、可验证，并能说明发生了哪些有损转换。
- 桌面和移动端不再分别实现一套互相漂移的谱面语义。

## 3. 已确认的需求与优先级

### 3.1 已确认方向

- 图层是**可复用的 Note 集合和编辑边界**，不是单纯的绘制层。
- 一个图层可以被多个难度引用，用于直接复用共同段落或基础物量。
- 图层必须具备常规编辑器能力：新建、重命名、排序、复制、剪切、粘贴、跨层移动，以及把选中 Note/图层转移或复制到其他 `.mc` 难度。
- “新建 MC”在工程内建模为新建 Difficulty，可从空白、现有难度或指定图层组创建；不得靠未受控的文件复制维持多难度状态。
- 多 `.mc` 同时加载主要用于**跨难度参考**，不自动视为当前难度的可导出图层。
- 导出 `.mc` 时由谱师手动选择图层、选择图层组，或使用保存的导出配置。
- Meta 使用字段级策略：歌曲级字段可同步，难度字段可继承或覆盖，难度名等字段必须手动确认；同步不得静默覆盖已有覆盖值。
- 评论可以锚定单个 Note、多个 Note、时间/X 区域，也可以不绑定 Note。
- 修改建议应接近代码审查：建议本身不直接改主谱，由作者接受、拒绝或处理冲突。
- osu!ctb 需要读取、编辑、导出和与 Malody Catch 互转的配置能力。
- 其他模式转换为低优先级，是否实现取决于实际需求。
- 实时 P2P 多人制谱仅作为远期可选项。
- 备份和版本历史采用 Git-like 语义，但不要求内部真正依赖 Git。
- 内部工程格式可以扩展或变化，只要始终能够导出标准 `.mc`。
- 底层能力应尽量可供其他制谱器复用。

### 3.2 优先级

| 级别 | 方向 |
|---|---|
| 近期主线 | CCE 稳定性、内部文档边界、持久 ID、revision、类型化变更、MainWindow 解耦 |
| 中期主线 | 工程格式、多难度、图层/图层组、跨难度参考、显式导出 |
| 中后期 | 本地审图、修改建议、自动备份和命名版本 |
| 后期 | osu!ctb 原生支持和可配置转换 |
| 条件并行 | 移动端兼容子集 |
| 远期可选 | 通用核心独立成仓、实时 P2P、其他模式转换 |

## 4. 仓库与事实来源策略

### 4.1 当前事实来源

在通用核心正式拆分并通过验收前：

- `Malody_catch_editor` 是 Malody Catch 编辑行为的唯一事实来源。
- 当前桌面测试、格式回归和性能基准具有最高优先级。
- 新架构先作为 CCE 仓库内的独立 CMake target 和目录边界演进。
- 不再通过手工复制 `Chart`、`ChartController` 或 `ChartIO` 来“同步核心”。

### 4.2 旧 `Malody_catch_core`

旧核心来自约 CCE 1.6.0 时期的拆离，之后增加了纯 C++ 模型、C ABI4、Android 构建、错误码和符号门禁，但核心语义严重落后于当前桌面端。

保留价值：

- 独立 CMake 构建经验。
- 纯 C++ 与 C ABI 的工程骨架。
- FFI 错误契约、符号检查与负向测试。
- Android arm64 构建和产物同步经验。
- 作为迁移失败模式与兼容性需求的样本。

不可直接沿用的部分：

- 绑定 Normal/Sound/Rain 和 `0..512` 的所谓通用模型。
- 每次编辑保存整张 Chart 前后副本的历史实现。
- 可绕过 revision/undo 的 `mutableChart()`。
- 按数组下标拉取快照、每次 revision 全量刷新客户端的 FFI 访问方式。
- 旧 Qt transitional 源码副本。
- 将文档或局部补丁更新等同于完整桌面语义同步的基线描述。

处置原则：旧仓库保持可追溯，不作为新开发主线。待新内部核心稳定后，再决定将其归档、转换为兼容维护仓，或由新拆分仓替代。

### 4.3 旧移动端尝试

`Malody_catch_mobile` 继续作为以下资产保留：

- Flutter/Android UI 与手势实验。
- FFI 客户端和错误展示样例。
- Android 文件选择、分享、音频和生命周期处理经验。
- 第二消费者的兼容性测试场。

它不作为领域模型的事实来源。移动端重复实现的 `.mc` 编解码、超大控制器和旧 ABI4 绑定应在新接口成熟后逐步替换，而不是继续扩展。

### 4.4 `malodycatch2ctb`

父目录中的转换仓库在 osu!ctb 阶段作为行为样本、测试语料和转换规则来源进行独立审计。它不会未经验证地直接并入核心。

## 5. 术语与边界

### 5.1 Song Project

一个歌曲级编辑工程，拥有资源、时间轴、难度、图层库、评论、版本和导出配置。工程是编辑器完整状态的持久化边界。

### 5.2 Difficulty Document

一个可发布难度，拥有：

- 难度元数据。
- 所使用的时间轴。
- 有序的图层引用列表。
- 默认导出配置。
- 难度级校验结果。

Difficulty 自身不复制共享图层中的 Note。

### 5.3 Note Layer

真正拥有 Note 的数据容器。每个 Note 在任意时刻只属于一个图层。

图层具有稳定 ID、名称、颜色、可见性、锁定状态、时间轴归属和导出资格。可见性、颜色等视图属性可以允许按难度覆盖，但 Note 内容仍由图层本体拥有。

### 5.4 Shared Layer 与 Local Layer

- Shared Layer：被多个难度引用；一次编辑会影响所有引用难度。
- Local Layer：当前只被一个难度引用，但数据结构与 Shared Layer 相同。

“共享/本地”由引用数量和策略决定，不设计两套 Note 容器。

### 5.5 Layer Group

图层 ID 的命名集合，用于：

- 批量显示、隐藏、锁定和独奏。
- 快速选择编辑范围。
- 保存常用导出组合。

第一版不支持递归嵌套组；一个图层可以属于多个组。组只引用图层，不复制 Note。

### 5.6 Reference Chart

作为背景参考叠加的其他难度或外部 `.mc`。Reference Chart：

- 默认只读。
- 不属于当前 Difficulty 的合成内容。
- 永远不会被无意导出。
- 可以将选中 Note 复制/提取到当前工程的某个图层，提取时生成新的持久 ID。

### 5.7 Export Profile

保存目标难度、选中图层/图层组和导出校验策略的配置。手动勾选仍始终可用。

### 5.8 Revision、Undo、Recovery 与 Version

- Revision：每次成功提交事务后的单调版本号，用于缓存和并发结果判旧。
- Undo/Redo：当前编辑会话中的短期交互历史。
- Recovery：崩溃恢复用滚动快照，不等同于用户版本。
- Version/Checkpoint：用户可命名、可长期保留的工程版本。

四者不得继续混用同一套生命周期。

### 5.9 Metadata Field Policy

多难度工程不把 Meta 简化成“全部同步”或“全部独立”，而是为每个字段记录策略：

| 策略 | 典型字段 | 新建 Difficulty 时 | 后续同步 |
|---|---|---|---|
| Project Shared | 标题、原始标题、曲师、原始曲师、音频、背景、试听时间 | 自动引用工程值 | 工程值修改后自动传播；允许显式转为覆盖 |
| Inherit with Override | 谱师、默认速度及未来可继承字段 | 从模板/工程默认值初始化 | 未覆盖时跟随；已覆盖值只在用户确认后替换 |
| Required per Difficulty | 难度名/`version`、目标导出文件名 | 必须手动填写或确认 | 永不被批量同步静默改写 |
| Structural Reference | Timeline、BPM、offset 和资源绑定 | 明确选择共享、克隆或新建 | 通过专用事务变更，不混入普通 Meta 文本同步 |

Meta 面板最终应显示字段来源（工程共享、继承、当前难度覆盖、待填写），支持预览差异、选字段同步、恢复继承和批量校验。导出时先解析“有效 Meta”，并阻止缺少必填字段的目标 Difficulty。

## 6. 拆仓前的 CCE 内部目标架构

CCE 先在单仓库内形成以下依赖方向：

```text
Qt Widgets UI
    │
    ▼
Editor Services / Coordinators
    │
    ▼
Document + Command + Read Model
    │
    ├── Malody Catch Rules
    ├── Format Codecs
    ├── Conversion Services
    └── History / Review / Project Storage
```

推荐的内部 target/目录职责：

| 边界 | 职责 | 禁止依赖 |
|---|---|---|
| `cce_domain` | ID、精确时间、实体、图层、难度、事务、revision | QtWidgets、音频、MainWindow、文件对话框 |
| `cce_rules_malody_catch` | Normal/Rain/Sound、坐标和玩法校验 | UI 状态、文件选择 |
| `cce_document` | 工程、合成视图、历史、评论、恢复接口 | MainWindow、具体控件 |
| `cce_formats` | `.mc/.mcz` 及未来 `.osu/.osz` codec | 编辑工具状态 |
| `cce_editor_services` | 当前文档、命令分发、选择、剪贴板、后台任务 | 具体窗口布局 |
| `CatchChartEditor` | Qt UI、画布、面板、对话框、音频装配 | 反向成为数据事实来源 |

初期允许无界面层继续依赖 QtCore，以降低重构风险；不得依赖 QtWidgets 或全局 UI 单例。是否将公共接口进一步改为标准 C++，留到真实第二消费者接入后决定。

### 6.1 MainWindow 拆分

`MainWindow` 最终只负责窗口级装配和命令入口。按真实职责逐步迁出：

- `SessionCoordinator`：打开、替换、恢复和关闭会话。
- `WorkspaceController`：歌曲工程、难度和图层生命周期。
- `DocumentController`：活动文档、事务、dirty 状态和保存。
- `CommandRouter`：菜单、快捷键、画布和面板命令统一路由。
- `ResourceCoordinator`：音频、背景、sidecar、转换和路径处理。
- `PluginUiCoordinator`：插件动作、面板和 capability 协商。
- `DiagnosticsCoordinator`：诊断导出与性能会话。

拆分以行为测试为前提，禁止一次性重写整个 MainWindow。

### 6.2 画布与主编辑区

画布不再取得可变 `Chart *`，而是读取版本化的 `ComposedChartView`：

- 每个可见对象带 `(LayerId, EntityId)` 来源。
- 选择、命中、拖动和删除基于 ID，不基于排序后的数组下标。
- 拖动过程只维护轻量预览；松手后提交一个事务。
- 图层数据和参考谱面分别维护排序索引。
- 只在数据、时间轴或可见性 revision 变化时重建合成索引。
- 绘制帧不得重新拼接、复制或全量排序所有图层。

保留当前 QWidget/QPainter 渲染路线，除非性能数据证明需要更换后端。

## 7. 数据与事务模型

### 7.1 持久实体标识

工程内的 Project、Difficulty、Timeline、Layer、Note、Comment 和 Version 都使用持久 ID。标准 `.mc` 不携带编辑器 ID；首次导入时生成，之后保存在工程格式中。

要求：

- ID 不因排序、保存、重启或切换难度变化。
- 复制 Note 生成新 ID；移动 Note 保留 ID。
- 共享图层被多个难度引用时不复制其 Note ID。
- 旧 sidecar 关联数据导入时需要明确的匹配和迁移报告。

### 7.2 精确时间

- Malody 拍点使用规范化有理数比较，不以 `double` 作为排序真相。
- 每个图层绑定一个 Timeline。
- 同一 Timeline 的图层可以直接复用。
- Timeline 不同的内容不得静默合并。
- 跨难度参考按绝对音频时间对齐，再投影到活动难度网格。
- 将参考内容提取为可编辑 Note 时，必须选择量化/重映射策略并显示误差。

### 7.3 类型化事务

所有修改通过可验证、可序列化的事务提交：

```text
Transaction
├─ transactionId
├─ baseRevision
├─ author / timestamp / description
└─ operations[]
   ├─ AddEntity
   ├─ RemoveEntity
   ├─ SetEntityProperty
   ├─ MoveEntityToLayer
   ├─ Add/RemoveLayerReference
   └─ UpdateMetadata/Timing
```

要求：

- 一个用户动作只产生一个 revision。
- 验证失败时整批拒绝，不产生部分修改。
- Undo 保存逆操作或紧凑 delta，不保存两份完整工程。
- 事务提交后产生 typed change set，供渲染、统计、密度、选择和保存精确失效。
- 对旧插件的整谱替换保留有界兼容路径，但不得成为正常编辑方式。

### 7.4 规则集扩展

通用实体只包含 ID、图层、时间锚点和规则集类型标识。具体玩法字段由规则集拥有：

```text
ChartEntity
├─ EntityId
├─ LayerId
├─ TimeAnchor / TimeSpan
├─ RuleSetId
├─ ObjectTypeId
└─ RuleSetPayload
```

核心不得假设所有模式都拥有 X、轨道、长按或 `0..512` 坐标。Malody Catch 和 osu!ctb 是前两套真实规则实现；只有经两者验证确实通用的概念才上移到公共层。

## 8. 图层、跨难度复用与导出

### 8.1 基本编辑规则

- 始终存在一个活动 Difficulty 和一个活动可编辑 Layer。
- 可跨多个未锁定图层框选和批量编辑。
- 新建 Note 默认进入活动图层。
- “移动到图层”保留 Note ID；“复制到图层”生成新 ID。
- 复制/剪切/粘贴的剪贴板记录来源 Difficulty、Layer、Timeline、相对拍点和对象类型；粘贴目标默认是活动图层，也可在确认前改选目标图层。
- 剪切、跨层移动和跨 Difficulty 转移必须是单个原子事务：目标写入失败时源内容不删除，Undo/Redo 一步恢复完整操作。
- 跨 Difficulty 复制生成新 ID；跨 Difficulty 移动仅在同一工程内保留 ID，并同步迁移评论/选择等引用关系。
- 来源与目标 Timeline 不同时必须打开重映射预览，按绝对音频时间对齐并显示量化误差，禁止静默按拍号直接粘贴。
- 锁定图层仍可显示和参与播放，但不能被编辑命令修改。
- Solo/可见性只影响视图，是否导出由 Export Profile 独立决定。

### 8.2 共享安全

编辑被多个难度引用的图层时，界面必须显示共享标识和受影响难度数量。高影响操作提供：

- 继续编辑共享图层。
- 派生为当前难度的独立副本。
- 取消操作。

删除共享图层前必须列出所有引用；不得留下悬空引用。

### 8.3 跨难度参考

Reference Chart 支持：

- 每个参考难度独立颜色、透明度、显示/隐藏和偏移校准。
- 以幽灵样式绘制，不与当前层选择状态混淆。
- 同歌同时间轴时直接对齐；不同 BPM/offset 时按音频时间对齐。
- 从参考中复制单个、多个或时间范围内的 Note。
- 缺失或外部文件变化时显示路径/hash 状态，不静默替换参考内容。

### 8.4 Difficulty / `.mc` 生命周期

工程级常用操作至少包括：

- 新建空白 Difficulty（UI 可显示为“新建 MC”）。
- 复制 Difficulty；可选择仅复制结构、复制本地图层，或继续引用共享图层。
- 从 Layer Group/手动图层集合创建 Difficulty。
- 将选中 Note、完整 Layer 或 Layer Group 复制/移动到目标 Difficulty。
- 将外部 `.mc` 作为只读 Reference 打开，或显式导入为工程 Difficulty。
- 删除 Difficulty 前列出专属图层、共享引用、评论、版本和导出配置影响。

新建流程先选择 Timeline/模板与 Meta 继承策略，再要求确认难度名和导出文件名；创建、资源引用、图层引用和 Meta 初始化作为一个事务提交。

### 8.5 Meta 同步与批量填写

- 工程提供“同步 Meta”差异视图，可按字段、按目标 Difficulty 勾选，不提供无预览的全量覆盖按钮。
- Project Shared 字段默认实时一致；Difficulty Override 明确显示“跟随/已覆盖”。
- 新建 Difficulty 自动带入歌曲级信息，难度名必须手动确认；谱师、速度等字段可由模板预填但仍可覆盖。
- Timeline/BPM/offset 的共享或复制是结构操作，需要单独确认受影响 Note 与时间对齐，不借 Meta 同步暗改。
- 批量同步、恢复继承和手动填写均进入事务/Undo、审图差异和版本历史。
- 保存/导出校验列出缺失字段、非法资源引用和跨难度不一致，但不会擅自修改用户数据。

### 8.6 标准 `.mc` 导出

导出必须是显式、确定性的投影：

1. 选择目标 Difficulty。
2. 选择 Export Profile、Layer Group 或手动图层集合。
3. 检查所有图层是否使用兼容 Timeline。
4. 扁平化选中图层并稳定排序。
5. 校验重复 Note、越界、Rain 区间、音频引用和不受支持对象。
6. 展示 Note 数量、来源图层和警告摘要。
7. 原子写入标准 `.mc`；可选继续打包标准 `.mcz`。

原则：

- 不自动删除同时间同 X 的 Note，只警告。
- Reference Chart 默认无法直接进入导出；必须先提取为工程图层。
- 评论、版本、图层 ID、审图状态和转换报告不写入 `.mc`。
- 相同工程 revision、相同 Export Profile 应产生逻辑等价且顺序确定的谱面内容。

## 9. 编辑器工程格式

### 9.1 定位

标准 `.mc` 是交换和发布格式；工程格式是完整编辑状态的事实来源。工程格式名称和最终扩展名在实现 RFC 中确定。

建议先使用目录式工作工程，便于恢复、增量写入和诊断；稳定后可增加单文件打包形式用于分享。

建议逻辑结构：

```text
project.json
resources/
timelines/
layers/
difficulties/
reviews/
history/
conversion-profiles/
legacy-sidecars/
```

### 9.2 必需能力

- 根清单包含 `schemaVersion`、ProjectId、资源清单和引用关系。
- 确定性序列化，支持语义 diff 和内容哈希。
- 每次 schema 变化提供单向迁移器、备份和迁移报告。
- 清单和关键数据使用原子替换；崩溃恢复不覆盖最后一次用户版本。
- 文件引用执行与现有恢复系统相同等级的根目录、遍历和链接逃逸检查。
- 资源按 hash 识别，避免仅凭同名文件判断一致性。
- 未识别的规则集载荷和可安全保留的格式扩展不得在普通保存时丢失。

### 9.3 兼容导入

打开传统 `.mc` 时：

- 创建一个 Song Project。
- 创建一个 Difficulty。
- 创建一个 `Base` 图层。
- 将 `.mc` Note 导入 `Base`。
- 生成工程内持久 ID。
- 收集音频、背景和现有 sidecar。

用户不启用工程功能时，仍可沿用当前 `.mc` 打开、保存和 `.mcz` 导出工作流。

## 10. 评论、审图与修改建议

### 10.1 评论线程

Review Thread 至少包含：

- 稳定 ID。
- 作者、创建时间和最后更新时间。
- `open / resolved / outdated` 状态。
- 一个或多个评论条目。
- 锚点和可选修改建议。

锚点同时保存：

- 目标 Note ID 列表。
- 时间点或时间范围。
- 可选 X 点或 X 范围。
- 创建时的范围快照。

因此 Note 被移动或删除后，评论仍能显示在原始时空位置并标记为过期，而不会无提示消失。

### 10.2 修改建议

修改建议保存为基于 `baseRevision` 的事务补丁：

- 审图者提交建议不会直接修改主谱。
- 作者可以预览前后差异、接受、拒绝或部分应用。
- 基础对象已改变时执行属性级冲突检查。
- 已接受建议进入正常版本历史，并记录建议来源。

第一阶段只支持本地和文件交换；网络身份、权限和实时通知不属于初版范围。

## 11. 备份与 Git-like 版本控制

版本能力分层实现：

| 层级 | 用途 | 保存策略 |
|---|---|---|
| Undo/Redo | 秒到分钟级交互撤销 | 内存中的紧凑事务与逆操作 |
| Recovery | 崩溃恢复 | 防抖快照与有限滚动保留 |
| Auto Snapshot | 定期备份 | 后台、按时间/变更量触发、可清理 |
| Checkpoint | 用户命名版本 | 长期保留、作者/说明/父版本 |
| Branch/Merge | 未来并行方案 | 在审图补丁稳定后再实现 |

底层可以使用内容寻址快照、事务 delta 和周期性完整快照，但不要求用户安装 Git，也不直接把运行中的工程变成 Git 仓库。

要求：

- 版本保存不能阻塞播放或主编辑线程。
- 历史空间与“变更量”近似相关，不能是“整谱大小 × 编辑次数”。
- 资源大文件按 hash 去重。
- 恢复、自动快照和用户 Checkpoint 使用不同保留策略。
- 提供按 Note、图层、时间范围和元数据分类的语义差异。

## 12. osu!ctb 与格式转换

### 12.1 两条独立能力

osu!ctb 支持必须区分：

1. **原生 osu! 文档编辑**：保留 slider、spinner、TimingPoint、SV、hitsound、combo 和未编辑段落，并能再次导出 `.osu`。
2. **转换到 Malody Catch**：将 osu! 对象映射/展开为 Malody Catch 可表达内容，并输出标准 `.mc`。

将 slider 展开为离散物量后通常无法无损恢复原始 slider；产品和 API 不得把有损转换标成“往返兼容”。

### 12.2 转换配置

转换配置至少包括：

- offset 和音频时间基准。
- 拍点量化精度与最大容差。
- 红线 BPM 与绿线 SV 处理。
- slider 起点、尾点、tick 和 tiny droplet 采样策略。
- spinner/banana 转换策略。
- X 取整、夹取和冲突策略。
- hitsound/combo 等不可表达信息的保留或丢弃策略。
- 重复 Note 和超密对象处理。

每次转换产生机器可读和用户可读的损失报告，列出：

- 被忽略的对象与字段。
- 被量化的时间及误差。
- 被展开/合并的对象数量。
- 无法反向恢复的语义。
- 导出警告和阻断错误。

### 12.3 其他模式

其他模式只通过新的 Ruleset + Codec + Converter 注册边界接入。不得为尚无实现计划的模式提前在公共实体中堆积字段。

## 13. 移动端兼容路线

移动端允许比核心拆仓更早推进，但必须满足“兼容优先、范围受控”。

### 13.1 开始条件

满足以下条件后，可以在 CCE 仍为单仓库时构建移动端使用的无界面产物：

- 持久 ID、revision 和事务语义已在桌面端稳定。
- 无界面 target 不依赖 QtWidgets、MainWindow、音频 UI 或全局 Settings。
- C API/消息协议具备版本协商、长度安全字符串和批量增量读取。
- 桌面与无界面 API 通过同一套操作回放测试。
- Android 构建可由 CI 从指定 CCE commit 重现，不再依赖手工复制未知来源 `.so`。

### 13.2 移动端首批范围

建议首批仅包含：

- 标准 `.mc/.mcz` 打开、基础编辑、保存和导出。
- 单 Difficulty、单 Base Layer。
- 稳定 ID、批量事务和 Undo/Redo。
- 基础音频播放与时间定位由移动应用层负责。

随后按兼容性逐步增加：

- 工程只读或简化打开。
- 图层显示、切换和有限编辑。
- 评论查看与回复。
- Checkpoint 查看和恢复。

不要求移动端立即达到桌面完整面板、插件、复杂曲线和高级审图能力。

### 13.3 与旧移动端的关系

- 保留现有 Flutter UI、文件、分享、音频和测试资产。
- ABI4 只作为旧实现兼容线，不限制新模型。
- 新接口使用独立版本或新符号前缀，迁移期间允许双栈。
- 新接口稳定并完成迁移后，再决定停止 ABI4 维护。

## 14. 通用核心复用与最终拆分

### 14.1 通用边界

未来可复用核心负责：

- Project、Document、Timeline、Layer、Composition。
- 持久 ID、事务、revision、历史和评论。
- 规则集、codec、转换和校验接口。
- 确定性序列化和 schema migration。
- 无界面查询、索引和批量数据访问。

不负责：

- Qt 窗口、画布控件和面板布局。
- 平台文件选择器。
- 音频设备和播放器 UI。
- 插件面板。
- 网络传输与 P2P 会话。

### 14.2 不提前拆分的原因

- 当前真实消费者仍只有桌面端。
- 图层、工程和评论语义尚未经过实际使用验证。
- osu!ctb 尚未成为第二套真实规则实现。
- 旧核心已经证明过早拆分会造成代码和行为漂移。
- 在接口仍变化时冻结跨仓 ABI 会显著增加维护成本。

### 14.3 拆分门槛

只有全部满足以下条件，才建立或替换独立通用核心仓库：

- 桌面 CCE 已连续至少两个稳定版本使用内部无界面 target。
- 移动端或另一个独立消费者正在使用相同领域实现，而非复制代码。
- Malody Catch 与 osu!ctb 两套规则/格式已经验证扩展接口。
- 核心公共层不依赖 QtWidgets、MainWindow、平台音频或应用单例。
- 增量事务、历史、迁移、格式 round-trip 和性能测试齐全。
- API/ABI 版本策略、发布产物、许可证和维护责任已经明确。
- 从 CCE 当前历史抽取可以保留可追溯提交，并有自动化集成测试阻止再次漂移。

拆分时优先从当前 CCE 内部 target 的历史抽取，而不是继续在旧 1.6-era core 上逐文件补齐。

## 15. 实时协作

实时多人制谱暂不进入近期里程碑。前置能力仍应为未来协作服务：

- 稳定实体 ID。
- 可序列化原子事务。
- base revision 和冲突检测。
- 评论线程与修改建议。
- 作者身份字段和版本历史。

如果未来实施，第一版建议使用房主权威的有序事务日志：

- 房主确认操作顺序和当前 revision。
- 客户端提交基于旧 revision 的操作时执行重放或冲突检查。
- 同一实体同一属性的并发编辑才需要人工处理。
- 音频和图片按 hash 同步，不混入高频编辑消息。
- P2P 只是一种传输方式，不与文档一致性模型绑定。

完整离线并发和 CRDT 仅在真实需求证明必要后评估。

## 16. 分阶段实施路线

### M0：当前维护线收口

目标：为架构演进建立可信基线。

状态：主要工作已完成，继续处理发现的确定性问题。

已具备：

- 原子保存和恢复路径安全。
- 批量 Note 变更。
- 拖动纯渲染预览。
- 类型化失效信号的初步边界。
- 后台统计与 stale-result guard。
- 大谱面播放与零预热启动基准。
- 主编辑区不可关闭/移动/浮动并具有最低可用尺寸；面板具有显式恢复入口；经典与多窗口布局分别持久化并独立重置；关闭紧凑工具块不会拉伸其余模块内容，浮窗不继承停靠态限高。

工作台布局子路线（参考已解压的 VS Code Workbench、Grid、SplitView、PaneView 与 Auxiliary Window 实现，只采用架构原则）：

1. **兼容阶段（当前）**：保留 ADS 存量布局格式；主编辑区成为稳定、不可折叠的中心 part，工具停靠约束与浮窗尺寸约束分离，拖拽轮廓动态显示落点。
2. **容器阶段**：引入 CCE 自有 `WorkbenchLayout`。Editor、Primary Sidebar、Auxiliary Sidebar、Bottom Panel 是稳定顶层 part；Note/Timing/Range 等不再直接成为全局 splitter 叶子，而由侧栏内部 `PaneContainer` 管理。
3. **Pane 阶段**：每个 pane 支持折叠、重排、复制/移动到允许的容器，按稳定 ID 保存展开状态、可见尺寸和原位置；隐藏/关闭 pane 时缓存尺寸，不把释放空间无条件投射到编辑区。
4. **辅助窗口阶段**：浮动不再等同于任意裸 Dock。独立窗口承载完整 pane container 与明确生命周期，提供“移回原位置/移动到...”入口，并按显示器保存边界；实时协作或多文档 UI 不依赖窗口实现。

在容器阶段完成前，不继续用更多硬编码 `maximumHeight`、splitter 比例或特殊浮窗分支堆叠行为；即时问题只能在 `DockLayoutPolicy` 兼容层内修复，并必须覆盖停靠、浮动、关闭、恢复与模式切换测试。

退出门槛：Release/Debug 测试通过，参考谱面基准稳定，未解决数据安全缺陷为零。

### M1：CCE 内部领域地基

目标：不改变用户工作流，消除后续功能的结构阻塞。

任务：

- 引入强类型 `EntityId/LayerId/DifficultyId/TimelineId`。
- 使用规范化有理数进行拍点比较和排序。
- 引入单调 revision 与 typed change set。
- 将选择从数组下标迁移到 EntityId。
- 建立事务/逆操作模型，逐步替代完整 Chart 快照。
- 增加只读 snapshot/read model，关闭 UI 直接取得 mutable Chart 的路径。
- 按职责拆出 MainWindow 协调器。
- 在同仓库建立无界面 CMake target。

退出门槛：现有单 `.mc` 工作流无行为变化；所有编辑命令可回放；参考谱面性能不回退。

### M2：工程、难度与图层模型

目标：建立完整 Song Project，并保持单 Base Layer 兼容。

任务：

- Project/Resource/Timeline/Difficulty/Layer/Composition 模型。
- 字段级 Meta 共享/继承/覆盖策略与有效 Meta 解析。
- 目录式工程格式、schemaVersion 和迁移框架。
- 传统 `.mc` 导入为单 Difficulty + Base Layer。
- ComposedChartView 与按 revision 维护的合成索引。
- 工程恢复、原子保存和资源 hash。
- Export Profile 核心流程，无需先完成全部 UI。

退出门槛：工程保存/恢复/迁移可验证；单层导出与当前标准 `.mc` 逻辑等价。

### M3：图层 UI 与跨难度参考

目标：交付首个用户可见的新工程工作流。

任务：

- 图层新建、重命名、排序、显示、锁定、独奏和颜色。
- 图层感知的复制、剪切、粘贴、跨层选择/移动/复制与批量事务。
- 新建/复制 Difficulty（“新建 MC”）、从图层组创建难度、跨 Difficulty 转移或复制 Note/Layer。
- Meta 差异视图、选字段同步、恢复继承和必填字段校验。
- Shared Layer 跨难度引用与派生。
- Layer Group 和手动导出选择。
- 多 `.mc` 只读叠加、时间对齐和 Note 提取。
- 导出预览、来源统计、冲突警告和确定性输出。

退出门槛：共享修改影响范围清晰；参考谱面不会误导出；多层大谱面达到性能门槛。

### Mobile Track A：基础兼容接入

开始时间：M1 接口稳定后，可与 M2/M3 部分并行。

任务：

- 从 CCE 指定 commit 自动构建移动端无界面产物。
- 设计新版本 C API/消息协议，不破坏旧 ABI4。
- 迁移移动端基础 `.mc` 编辑和批量事务。
- 建立桌面/移动操作回放一致性测试。

停止条件：如果移动适配迫使尚未验证的桌面领域接口提前冻结，则暂停移动线，优先完成桌面语义。

### M4：审图与本地版本

目标：支持非实时协作和可靠历史。

任务：

- 时空/Note 锚定评论。
- open/resolved/outdated 生命周期。
- 修改建议补丁、预览、接受和冲突处理。
- 自动快照、命名 Checkpoint、恢复与语义 diff。
- 可携带基础版本和建议的离线审图包。

退出门槛：删除/移动 Note 不丢评论；建议应用可撤销；长历史不会线性复制整谱。

### M5：osu!ctb 与转换

目标：先建立明确的保真边界，再扩展编辑体验。

- `.osu/.osz` codec 和源格式保留模型。

## 17. 性能与质量门槛

### 17.1 基准谱面

持续使用 `Yugami - Nyanpasu- Lv.16` 作为真实参考负载：

- 4,461 Note。
- 覆盖普通 Note、Rain、Sound 和高密度区间。
- 保持 Release 10 秒播放、零预热启动和多倍速矩阵。

同时增加合成负载：

- 5k、20k、100k Note。
- 1、10、50 个图层。
- 1、5、20 个参考难度。
- 1、100、4,000 Note 批量移动。
- 长 Rain、大范围框选、复杂评论锚点和长历史。

### 17.2 不变量

- 播放时 0 UI stall、0 由编辑器工作引起的跳帧。
- 播放启动显示时钟连续，不等待首个媒体位置回调。
- 绘制复杂度与可见对象近似相关，不与工程全部对象数量直接相关。
- 指针移动期间不提交事务、不写盘、不重建整谱缓存。
- 单次批量动作只产生一个 revision 和一个 Undo 步骤。
- 历史内存与 delta 大小近似相关。
- 后台结果携带 revision，过期结果不得覆盖新状态。
- 导入、保存、恢复、迁移和导出均有失败原子性测试。

每个里程碑开始前记录基线；关键指标相对上一稳定版本恶化超过 20% 时必须解释并获得明确收益，不能只以平均 FPS 掩盖交互尾延迟。

### 17.3 测试层级

- 领域单元测试：时间、ID、事务、图层引用、合成和冲突。
- 格式 golden tests：输入、规范输出、未知字段和损失报告。
- 操作回放：桌面、无界面接口和移动端执行相同序列。
- 属性/模糊测试：解析器、迁移器、路径和随机事务序列。
- UI 回归：图层状态、共享警告、参考不可导出、评论锚点。
- 性能基准：播放、编辑、合成、历史、加载和导出。
- 真实客户端验证：标准 `.mc/.mcz` 在 Malody 中打开和游玩。

## 18. 兼容与迁移策略

### 18.1 `.mc/.mcz`

- 永不向标准 `.mc` 写入 CCE 私有字段。
- 发布导出保持 Malody 兼容结构。
- 工程功能不可表达的数据只保存在工程格式。
- 每次工程保存后都可运行“标准导出可行性”检查。

### 18.2 Sidecar

- 当前 `.mcce-plugin` 数据继续可读。
- 工程首次导入时迁移可识别 sidecar，并保留源备份或迁移记录。
- 插件私有数据与核心图层/评论数据分开命名和授权。
- 未知 sidecar 不得因普通保存被删除。

### 18.3 插件

- 旧插件先看到活动 Difficulty 的扁平合成快照。
- 图层感知能力通过新 capability 和协议版本显式声明。
- 插件 delta 必须经过宿主验证并落为单一事务。
- 旧整谱 mutation 仅作为有界兼容路径，限制载荷、超时和历史占用。

### 18.4 项目降级

工程无法被旧 CCE 完整打开时，必须提供：

- 选择 Difficulty 和图层组合导出标准 `.mc`。
- 说明不会导出的评论、图层和历史数据。
- 在迁移前创建可恢复备份。

## 19. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 过早设计万能模型 | 只以 Malody Catch 和 osu!ctb 两套真实实现提炼公共能力 |
| 桌面、核心、移动再次漂移 | 拆仓前 CCE 为唯一事实来源；消费者运行同一操作回放测试 |
| 图层合成拖慢画布 | revision 驱动索引和可见集合；禁止逐帧拼接排序 |
| 共享图层误改多个难度 | 共享标识、影响数量、派生操作和删除引用保护 |
| 不同时间轴错误复用 | TimelineId 校验；跨轴只能显式重映射并报告误差 |
| 导出内容与视觉状态混淆 | 可见/锁定与 Export Profile 完全分离；导出前显示来源摘要 |
| 历史占用爆炸 | 事务 delta、逆操作、周期性快照、资源 hash 去重 |
| 工程格式升级损坏数据 | schema migration、原子替换、迁移备份和 golden tests |
| 移动端过早冻结 API | 版本化窄接口；不稳定时暂停移动线，不反向绑死桌面模型 |
| osu! 往返承诺不实 | 原生 round-trip 与有损转换分开，强制生成损失报告 |
| MainWindow 大爆炸重写 | 按职责逐项迁出，每一步保持测试和可运行状态 |

## 20. 已定决策与待定问题

### 20.1 已定

- CCE 先完善迭代，再考虑仓库级核心拆分。
- 移动端可以在兼容边界稳定后略微提前。
- 旧 core/mobile 不作为当前桌面语义事实来源。
- 图层拥有 Note，可跨难度共享。
- 多 `.mc` 用于只读跨难度参考。
- 图层组和手动图层集合都可以作为导出选择。
- 常规剪贴板、跨层/跨 Difficulty 转移与“新建 MC”属于首版图层工作流，不是后续附加项。
- Meta 采用 Project Shared、可覆盖继承、Difficulty 必填和结构引用四类字段策略。
- `.mc` 始终保持标准兼容，工程数据另存。
- 实时 P2P 延后且可能不实现。
- 其他模式转换保持低优先级。
- 最终通用核心必须经过真实第二规则集和第二消费者验证。

### 20.2 待在对应 RFC 决定

- 工程格式名称、扩展名及目录/单包的最终交付形式。
- 各现有/未来 Meta 字段的默认策略，以及谱师字段是否默认使用用户身份资料。
- Shared Layer 是否需要“跟随最新/固定版本”两种引用模式。
- Layer Group 是否在后续支持嵌套。
- 评论作者身份、本地签名和审图包信任模型。
- osu!ctb 第一版原生可编辑对象范围。
- 新移动接口采用 C ABI、结构化消息协议或两者组合。
- 通用核心拆分后的 API/ABI、包发布和许可证策略。
- QtCore 依赖何时从公共边界移除。
- 实时协作是否需要离线并发与 CRDT。
